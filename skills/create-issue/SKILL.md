# create-issue — 要件と仕様を深掘りして Issue を作る

ユーザーの要望を、**実装者が仕様を問い返さずに着手できる粒度の GitHub Issue** にする。
Issue を作成したらそこで終わり — 実装もブランチ作成もしない。

**全体方針**: ゴール合意 → 必要なときだけコード調査 → **仕様の深掘り（必須）** → テンプレに流し込み → `gh issue create`。

**深掘りは短縮の対象にしない。** 一文の要望をそのまま「背景 + 受け入れ条件2行」に整形して出すのは、このスキルの失敗パターン。曖昧さは消えておらず、実装フェーズで往復に化けるだけ。**深掘りにかけた1ラウンドが、実装での5ラウンドを防ぐ。**

---

## Phase 1: 要件を固める

### 0. まずゴールを明確にする（必須）

「この Issue が達成したいゴール（誰の・どんな課題を・どう解決するか）」を必ず言語化して合意する。曖昧なまま調査や作成に進まない。

- **可能な限り選択させる形にする。** 要望から想定されるゴールの候補を 2〜4 個立て、`AskUserQuestion` で提示する。最も妥当と思うものを先頭に置き、ラベル末尾に「（推奨）」。
- 要望が一文でゴールまで言い切っている場合でも、**自分の理解したゴールを一言で明示してから進む**。
- ここで固めたゴールが、Issue 本文の「背景 / 目的」と受け入れ条件の土台になる。

### 1. 調査が要るかを先に判断する

要望が既に実装可能な粒度で具体的（対象ファイル・挙動が明確、または新規の独立機能でフック地点が自明）なら**調査をスキップ**して Phase 1.5 へ。**深掘りはスキップしない。**

既存コードのフック地点や再利用箇所を特定しないと粒度が定まらない場合だけ調査する。

### 2. 調査は委譲する

読み取り専用の調査は、外部 CLI（`codex exec` 等）が使えるならそこへ、無ければ読み取り専用のサブエージェントへ委譲する。**結論だけ返させる**（ファイルダンプを持ち帰らせない）。

聞くのは5点だけ。各1〜3行で返させる。

1. フック地点（`file:line`）
2. 再利用できる既存関数 / パターン
3. 影響ファイル
4. 守るべき規約（リポジトリの `CLAUDE.md` 等）
5. 懸念点

外部 CLI をバックグラウンドで走らせるなら `< /dev/null` を付ける（付けないと stdin 待ちでハングする）。**前景の sleep ループで完了待ちしない。**

---

## Phase 1.5: 仕様を深掘りする（必須・短縮しない）

ゴールが決まっても、仕様はまだ決まっていない。**下の観点を1つずつ潰してから**本文を書く。

### 潰す観点

該当しないものは「該当なし」と判断して落としてよい。**黙って飛ばさない。**

1. **主要ユースケース / フロー** — 「誰が・どういう状況で・何をして・何が起きるか」を最低1本。分岐があれば複数本。UI が絡むなら画面遷移・操作順まで
2. **入力と出力** — 何を受け取り、何を返す / 表示するか。単位・形式・上限
3. **異常系・エッジケース** — 空 / 0件 / 大量 / 重複 / 権限なし / ネットワーク失敗 / 同時操作。**「そのときどうするか」まで決める**
4. **状態とデータ** — 永続化するか、どこに置くか、既存データとの整合、マイグレーションの要否
5. **対象ユーザー・権限** — 誰に見えて誰に見えないか
6. **既存機能との干渉** — 既存の似た機能と共存するのか置き換えるのか。壊れうる既存挙動
7. **非機能** — 必要なときだけ（性能・アクセシビリティ・i18n）
8. **明確なスコープ外** — 「今回やらないこと」を**必ず1つ以上**出す。出せないなら、まだスコープを絞れていない

### 各観点の埋め方（この順で判断する）

- **(a) 自分で決められるなら決める。** 慣習的な既定があるもの、コードを見れば分かるもの、答えが1つしかないものは聞かない。**決めたら本文に「前提」として明示する**（黙って決めない）
- **(b) 答えによって Issue の中身が変わるなら聞く。** `AskUserQuestion` で選択式。**独立した論点は1回にまとめて最大4問**
- **(c) 決められず、聞いても今は答えが出ないものは「未決事項」として残す。** 曖昧なまま受け入れ条件に混ぜない

**質問の総量は最大2ラウンド**（Phase 1 のゴール確認と合わせて）。超えるなら残りは (a) 前提として決めるか (c) 未決事項に落とす。

### 受け入れ条件の品質ゲート

Phase 2 に進む前に自己チェックする。

- [ ] 各条件が**第三者に検証可能**か（「正しく動く」「使いやすい」等の曖昧語が入っていないか）
- [ ] 正常系だけでなく、**洗い出した異常系が少なくとも1つ**条件に入っているか
- [ ] 条件が**ゴールを満たすのに十分**か（全部満たしてもゴールに届かないなら足りない）
- [ ] **スコープ外**が明記され、条件がそこに踏み込んでいないか

満たさない項目があれば Phase 1.5 に戻る。

## Phase 2: Issue を作る

### 本文の形

**Phase 1.5 で潰した内容を必ず本文に落とす**（自分の頭の中で解決して本文に書かない、が一番よくある取りこぼし）。

```markdown
## 背景 / 目的
（誰の・どんな課題を・どう解決するか）

## 主要ユースケース
- （〜な状況で、ユーザーは〜する → 〜が起きる）

## 要件
### やること
-
### やらないこと（スコープ外）
-

## 仕様
（入出力・状態/データ・対象ユーザーと権限・既存機能との関係。決めたことを断定形で書く）

## 異常系 / エッジケース
- （ケース → そのときの挙動）

## 前提（このIssueで決め打ちしたこと）
- （実装者が覆せるよう根拠を1行添える）

## 受け入れ条件
- [ ] （検証可能な条件。異常系も最低1つ含める）
```

該当がなければ節ごと落としてよいが、**「主要ユースケース」「やらないこと」「受け入れ条件」は必ず埋める**。

- 未決事項があれば `## 未決事項` を足し、`- [ ] （論点） — 決まらないと〜が確定しない` の形で残す
- **Phase 1 で調査した場合のみ**「実装方針（フック地点 `file:line`）」「影響ファイル」を足す。調査していない要望に実装方針を憶測で書かない

### 発行

**既定は `--body-file`**（節が多く改行整形が要るため）。一時ファイルに書いてから発行する。

```bash
gh issue create --title "..." --body-file <path> --label "status: todo"
```

本文が数行に収まるときだけ `--body "..."` でよい。

### 進捗ラベル

起票した Issue には `status: todo` を付ける。ラベルが未整備のリポジトリでは、無いものだけ1度作る（`--force` は既存を壊さない）。

```bash
gh label create "status: todo"        --color d4c5f9 --description "起票済み・未着手" --force
gh label create "status: in-progress" --color fbca04 --description "実装中" --force
gh label create "status: in-review"   --color 1d76db --description "PR作成済み・レビュー待ち" --force
gh label create "status: blocked"     --color b60205 --description "ブロック中・要ユーザー入力" --force
gh label create "status: done"        --color 0e8a16 --description "完了・マージ済み" --force
```

付け替えは常に「新 status を付ける + 旧 status を外す」で行い、同時に複数の `status:` が付かないようにする。

```bash
gh issue edit <N> --add-label "status: in-progress" --remove-label "status: todo"
```

作成された Issue の URL / 番号を報告して完了。

## 守ること

- **Phase 1.5 はスキップ禁止。** 「要望が明確そうだから」は理由にならない — 明確なのはゴールであって、異常系・スコープ外・前提はまだ決まっていない。省略してよいのは個々の観点が該当しないときだけで、工程そのものは飛ばさない
- **深掘り＝質問の連発ではない。** 大半は自分で決めて「前提」として明記する。ユーザーに投げるのは「答えで Issue の中身が変わる論点」だけ
- **ユーザーへの問いかけは原則 `AskUserQuestion`（選択式）。** 候補 2〜4 個、推奨を先頭、独立した論点は1回にまとめて最大4問。地の文で自由記述を求めてよいのは、値そのものを聞くとき（URL / ID / 具体的な文言）と、認証など人手操作しかないときだけ
- **Issue 作成でこのスキルは完了。** 実装・ブランチ作成・コミット・push・PR はしない。実装まで回したいなら `ship` を案内する
- **秘密の値をチャットや Issue 本文に出さない**（マスクや部分表示も含めて）
- Issue 作成はこのスキルの発動自体を承認と見なしてよい。それ以外の外向き操作はしない

## 完了報告

判断・調査・トレードオフを伴ったなら、結果を **Artifact** として公開して共有する。必ず載せる項目:

- 作成した Issue の番号 / URL / タイトル
- 主要ユースケースと受け入れ条件
- **異常系として拾ったケース**
- **決め打ちした前提**とスコープ外にしたもの
- 未決事項（あれば）

**Issue を1本作っただけ**で、それ以上の説明が要らないなら Artifact は作らず地の文でよい。

## 完了シグナル

実行を終えたら、必ず**独立した行に `result:` + 自己完結の一行ヘッドライン**を書いて締める。ブロック時は `needs input:`、構造的に不可能なら `failed:`。**最終ターンをツール呼び出しで終えない。**
